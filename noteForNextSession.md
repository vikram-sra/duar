# Duar.one — Architecture, Structure & Engineering Reference

This document serves as the single source of truth for the codebase architecture, asset pipelines, 3D coordinate spaces, rendering optimizations, and operational rules.

---

## 1. High-Level Concept & View Modes

**Duar.one** is an interactive, astronomical 3D web experience built with **Three.js** and **Vite**, transitioning seamlessly between three view modes:

1. **`default` Mode**:
   - The iconic gateway ring of monolith portal doors.
   - Central reflective monolith rock.
   - Time warp, day/night cycles, and portal travel physics.
2. **`portfolio` Mode**:
   - Concentric circular gallery rings of paintings by Vikram Sra.
   - Central interactive sculpture with dynamic ribbon thread physics.
   - Progressive multi-tier texture streaming (LOW -> MID -> FULL) with LRU caching.
3. **`forest` Mode**:
   - An authentic Indian orchard grove (*baag*) composed of **50 mature botanical trees**.
   - Balanced species tapestry: **2 grand sentinel Banyans**, **10 sacred Peepal / Bodhi trees**, **21 lush Mango trees**, and **17 graceful Neem trees**.
   - Central centerpiece: **Duar 3.0** (a blooming ruby red rose, *Rosa damascena*).
   - Fully procedural undulating terrain with organic wind-driven grass and dynamic sightline occlusion.

**Cross-view interaction rules** (these hold in all three modes):
- Clicking the centre object cycles `default -> portfolio -> forest -> default` and
  changes **only the contents of the world**. "Centre object" means whichever piece
  is central to the current view -- cone, sculpture, or the rose -- resolved through
  the single `CENTREPIECE_FOR` map that `switchView` also uses, so the thing you
  click and the thing that gets swapped cannot drift apart. The rose was previously
  excluded and routed to a camera focus instead, which made the same gesture do two
  different things depending on which world you were standing in. Camera position, zoom, time-of-day
  speed, pause state and dock visibility all survive untouched.
  `switchView(mode, { keepCamera: true })` is what does this, and it additionally
  clamps the incoming view's `minDistance` to the camera's current distance --
  otherwise OrbitControls shoves the camera outward when the new view wants a
  larger minimum.
- The play/pause control means the same thing everywhere: paused freezes the sky
  clock, the ground rings and the camera orbit; playing resumes all three. No view
  overrides it, and no flight-arrival callback decides for itself either -- they
  all restore `autoRotate = !motionPaused`.
- **The camera is never teleported.** The gallery's opening crane is gated on
  `_introStarted`; before that gate existed it re-armed on every entry to the
  gallery, snapping the camera 130 units up where it then stayed, because the
  intro itself correctly refused to replay. `onResize` glides rather than snaps,
  and leaves a deliberately-moved camera alone.

## 3. Core Subsystems

### A. Forest Engine (`src/portfolio/forest.js`)
- **`layoutForest()`**:
  - Deterministic Poisson disk / circle-packing layout using `mulberry32(80)`.
  - Places 50 trees within an outer radius of $68.0\text{m}$ and an inner clearing radius of $10.2\text{m}$.
  - Strict physical canopy radii ($12.65\text{m}$ Banyan, $7.15\text{m}$ Peepal, $8.15\text{m}$ Mango, $6.55\text{m}$ Neem) guarantee a minimum clearance gap $\ge 0.25\text{m}$ everywhere (zero crown collisions).
- **`getForestElevation(x, z)`**:
  - Analytical elevation function computing organic terrain topography:
    $$\text{elevation} = (h_1 + h_2 + h_3 + h_{\text{micro}}) \times \text{clearingFactor}$$
  - Shared identically by the ground vertex shader, tree base positioning, grass instances, and camera height clamp.
- **`preloadForestGLBs()` & `createTree()`**:
  - Loads GLB models once into a static cache (`_glbTreeCache`).
  - Instances are created via `template.clone(true)`.

### B. Master Controller (`main.js`)
- **`DuarApp`**:
  - Manages Three.js renderer, scene, camera, lights, OrbitControls, and GSAP transitions.
  - **`switchView(mode)`**: Transitions cameras, scales down prior objects, and dynamically builds the target mode.
  - **`focusFlora(door)`**: Camera framing for trees and Duar 3.0, ensuring full tree width and height are captured on mobile and desktop without distortion.
  - **`_updateForestFocusOcclusion()`**: Dynamic ray cylinder sightline test that hides foreground trees blocking the camera’s view of a focused tree or rose.

### C. Astronomical Celestial Lighting (`src/sky/celestial.js` & `main.js`)
- Dynamic 24-hour solar/lunar ephemeris cycle driving:
  - `this.sunLight` (DirectionalLight) & `this.sunMesh`
  - `this.moonLight` (DirectionalLight) & `this.moonMesh`
  - `this.hemiLight` (HemisphereLight) with ground/sky bounce grading
  - Procedural sky dome shader with day, dusk, twilight, and midnight palettes.

## 4. Critical Botanical & Model Calibrations

### Emergence animation
Trees scale in on a single `power2.out` over 4.2s, all three axes together, delayed by
distance from centre. **No `back.out`** -- overshooting past full size and settling back
reads as a rubber toy popping out of the soil on something 16m tall. Separate x/z and y
timings were also tried and compounded the problem by inflating the canopy after the trunk.

### Root Flare vs. Ground Sink (`groundSink`)
Artist 3D models often include subterranean roots extending far below the trunk base. Sinking incorrectly causes major visual regressions:
- **Too shallow (`0.35m`)**: Root claws hang in mid-air above the soil; tree looks uprooted and floating on spider legs.
- **Too deep (`3.5m`)**: Trunk is completely buried into the dirt; tree looks "stupidly short-trunked" with canopy leaves touching the grass.

**Exact Tested Calibration Profile (`src/portfolio/forest.js`):**
| Species | Target Height | `groundSink` | Root Anchor Status | Visual Trunk Height |
|---|---|---|---|---|
| **Peepal** (`bodhi_tree.glb`) | 20.0m | **`2.15m`** | Claws submerged $\ge 0.21\text{m}$ into soil | $3.5\text{m}-4.5\text{m}$ clear sculptural trunk + flutes |
| **Neem** (`neem_tree.glb`) | 16.0m | **`2.15m`** | Root claws firmly anchor into ground | $2.7\text{m}-3.0\text{m}$ slender clean trunk |
| **Mango** (`mango_tree_2.glb`) | 16.0m | **`0.08m`** | Natural ground contact | Full rounded dome |
| **Banyan** (`chinese_banyan...glb`) | 22.0m | **`0.12m`** | Prop roots touch ground naturally | Massive 28m aerial canopy |
| **Rose (Duar 3.0)** (`red_rose.glb`) | 1.45m | **`0.0m`** | Base sits flush at $(0, 0, 0)$ | Standing rose centerpiece |

The rose has **no painted contact-shadow disc**. It previously carried a 2.6m dark circle
under a 1.45m flower -- wider than the plant is tall, so it read as a disc drawn on the
grass. It casts a real shadow now that foliage sends and receives them.

**Outstanding:** `red_rose.glb` ships three 4096x4096 textures = **256 MB of GPU memory**,
73% of the scene's entire texture budget, for its smallest object. `red_rose.opt.glb`
(1024^2, 16 MB, 8.9 MB file) is built and validated but **not swapped in**.

*Rule*: **Never change Mango, Banyan, or Rose sinks when tweaking Peepal/Neem.**

## 5. Performance Invariants & GPU Rules

**Measured scene budget** (run `python3 scripts/../~/.claude/skills/threejs-experience/scripts/glb-audit.py public/models/*.glb --scene "neem_tree.glb=17,mango_tree_2=21,bodhi=10,banyan=2,red_rose.glb=1"`):

| species | count | tris each | total | share |
|---|---|---|---|---|
| neem | 17 | 217,378 | 3,695,426 | 43.5% |
| mango | 21 | 130,451 | 2,739,471 | 32.3% |
| peepal | 10 | 161,908 | 1,619,080 | 19.1% |
| banyan | 2 | 111,392 | 222,784 | 2.6% |
| rose | 1 | 214,660 | 214,660 | 2.5% |
| **TOTAL** | | | **8,491,421** | |

An earlier revision of this document recorded "~5.7M triangles". The real figure at
that time was **43.3M** -- the count had not been multiplied by GPU instance counts.
Always expand instancing before quoting a triangle budget.

1. **Neem is rebuilt from source, not downloaded (`scripts/build-neem-glb.py`)**:
   - The Sketchfab source is 3,004 meshes: 1 trunk (67,648 tris) + 1,000 leaf clusters
     of 2,196 tris each, for **2.26M triangles per tree**. All 1,000 clusters are
     byte-identical geometry differing only by parent matrix, so instancing them is
     lossless.
   - The leaves are already 2-triangle quads, ~820 per cluster. There is no per-leaf
     fat to trim; the only lever is **how many leaves there are**.
   - Rebuild with `python3 scripts/build-neem-glb.py --write`. Current settings:
     230 clusters, 26% of leaves kept, 1.4x leaf scale -> **217,378 tris**.
   - **Do not "preserve coverage" by scaling leaves up by `1/sqrt(fraction)`.** That
     was tried: it preserves projected leaf *area* while destroying *texture*, turning
     3cm leaflets into 20cm plates that hang in the branches like cardboard. Foliage
     reads as foliage because it is many small elements. Keep `--leaf-grow` near 1.4
     and buy density with `--clusters` and `--leaf-keep` instead.
   - The rebuild preserves the original material names (`Material.001`-`.004`) because
     `forest.js` keys foliage detection and shadow handling off those exact strings.
   - Height is preserved (maxY 1791 vs 1797), so the `groundSink: 2.15` calibration
     below still holds.
2. **Cached Shadow Map (`renderer.shadowMap.autoUpdate = false`)**:
   - Running shadow passes every frame over a scene this size cripples WebGL.
   - The shadow map is rendered once on entering the view or on tree emergence, and
     only recomputed when the sun angle moves by $\ge 0.008$ radians.
   - Resolution is **3072** on desktop (1024 mobile). At the 85-unit half-frustum that
     is ~5.5 cm per texel; the previous 1536 gave ~11 cm, coarser than a leaf, so
     leaf-on-leaf shadows could not resolve at all. Because the map is cached, a
     larger one costs memory (36 MB/light) rather than frame time.
3. **Foliage now receives shadows** (this reverses an earlier invariant):
   - Leaves both cast **and receive**. Skipping receive was correct at 43M triangles;
     at 8.5M the scene affords it, and without it a canopy takes no shadow from the
     branches above it or from neighbouring trees, so a grove renders uniformly bright.
   - Watch for shadow acne on leaves -- thin double-sided quads receiving shadows is
     the classic case. Raise `sunLight.shadow.normalBias` (currently 0.018) if it appears.
4. **Directional foliage shading (`applyFoliageSunShading` in `forest.js`)**:
   - Leaves are `DoubleSide` so they stay visible from behind, and Three pays for that
     by **flipping the shading normal on back faces** -- so a leaf lit from behind
     shades identically to one lit from the front and the canopy loses all light and
     shade. This shades against the *geometric* normal instead, which is not flipped.
   - Driven per frame by `updateForestLighting(dir, camera, strength)` from `main.js`,
     following whichever light is dominant. Strength is deliberately low under
     moonlight, where a hard lit/unlit split would read as daylight turned down.
4. **Direct Framebuffer Output in Forest Mode**:
   - In forest mode, `main.js` calls `this.renderer.render(this.scene, this.camera)` directly, bypassing `EffectComposer` multi-pass render targets and bloom blurs.
5. **Pixel Ratio Cap**:
   - `renderer.setPixelRatio(Math.min(window.devicePixelRatio, 1.5))` prevents 4K/Retina displays from quadrupling fragment shading load.

## 6. Naming & Nomenclature Rules

- The central rose is titled and named **`Duar 3.0`** (NOT "The Sacred Rose").
- Botanical descriptors avoid sacred/religious labels:
  - Peepal: `"Ficus religiosa · Bodhi Fig"`
  - Neem: `"Azadirachta indica · Indian Margosa"`

## 7. Build & Deployment Pipeline

- **Local Dev Server**: `npm run dev`
- **Production Build**:
  ```bash
  npm run build
  ```
  *(Executes `vite build && rm -rf docs && cp -r dist docs && touch docs/.nojekyll`)*
- Production assets are deployed from the `docs/` directory. Always run `npm run build` after modifying files in `src/` or `main.js`.
